## 1. Goal — walk-away mode

**Operator-stated goal**: hand a 30–40-PR plan to a long-running agent (or pool of agents) and walk away with high confidence that the outcome will match (or be better than) the architected specifications, without operator supervision during the run.

**Honest restatement** of what this architecture can promise (because over-promising is itself L4):

> Walk-away mode does not guarantee that 30–40 PRs will all merge. It guarantees that **for every PR the orchestrator produces, the operator has a server-side, audit-trail-backed, Tier-B-independent disclosure of what the PR did vs. what the plan asked for**, surfaced in a return-digest the operator reads when they walk back to the desk. PRs that should not have shipped will be visible as not-shipped (deferred, scope-reduced, or abandoned-with-replacement-PR), not as silently-broken-shipped.

The dishonest version of "walk-away" — "the agent will figure everything out and produce 40 perfect PRs" — is L4 partial-with-claim-of-complete. The honest version is "the agent will work through 40 PRs honestly, surface its own failures with structured disclosures, and the operator's first 5 minutes after walking back to the desk are spent reading a digest that names every gap and every deviation from the plan."

That second posture is what this architecture delivers.

**Key sub-properties of walk-away mode that v3.2 alone does not deliver**:

- **No silent stalls**: an agent stuck in a remediation loop must surface that fact to the orchestrator within a bounded iteration budget; the orchestrator decides whether to escalate, defer, or move on.
- **No silent main-breakage**: a PR merged earlier in the run must not silently break a PR three steps later in a way the orchestrator misses; cross-PR regression must be detected and surfaced.
- **No silent plan deviation**: if a PR ships scope different from the plan, that delta must be a structured artifact the operator can grep, not narrative buried in a PR body.
- **No silent dependency-on-future-PR**: if PR-N can't complete because it needs PR-M (where M > N in the plan order), the orchestrator must record a structured PIVOT_DISCLOSURE and either reorder or defer, not loop forever or ship a half-implementation.
- **No silent infra-as-code-failure conflation**: if a smoke or validator failure was caused by infrastructure (network out, runner OOM), it must be classified differently from a code failure, so the orchestrator's retry policy can be differentiated.

§2 maps each of these to an architectural mechanism.

## 2. The eleven walk-away failure modes (F1–F11) and which mechanism addresses each

Each failure mode is named, illustrated, and mapped to a phase + mechanism. Tier B should verify (a) this list is complete relative to the operator-stated goal, and (b) every mechanism is actually delivered in the named phase.

| # | Failure mode | Illustration | Addressed by | Mechanism |
|---|--------------|--------------|--------------|-----------|
| F1 | **Infinite remediation loop** | Tier A keeps producing diffs that each pass one rule and fail the next. 5-iteration cap fires; agent retries the same scope on the next PR; loop persists across PR boundaries. | Phase 4 | **Iteration budget at orchestrator scope** (cumulative across PRs in a lane); **forward-progress invariant** (BHS_OFFICIAL must trend upward across consecutive PRs in a lane, else lane is paused). |
| F2 | **Dependency on future PR** | PR-N implements feature X; the smoke can't pass without feature Y from planned PR-M (M > N). Agent stalls or fakes the smoke. | Phase 2 + Phase 4 | **PIVOT_DISCLOSURE schema** with `kind: deferred-on-dependency`; orchestrator's PR state machine recognises the kind and reorders the plan or marks PR-N as `awaiting: PR-M`. |
| F3 | **Unknown unknown plan deviation** | The plan assumed an internal API that doesn't exist; agent silently substitutes a different API and ships. | Phase 2 + Phase 5 | **Plan-intent vs. PR-actual diff** at PR open time (validator R10) + `PIVOT_DISCLOSURE: kind: scope-reduced` requirement when diff doesn't match plan; orchestrator's plan-disprove pre-flight catches the largest deviations before any code is written. |
| F4 | **Cumulative carry-forward debt** | Each PR adds one new Carried Debt item; after 30 PRs there are 30 items; block flag flips; orchestrator stops, but operator returns to a 30-item dump. | Phase 3 | **Quantitative cycle math + automatic block-flag** (already in v3.2 §6.3) **applied per-orchestrator-run** (Phase 4 wires the orchestrator to honor the block flag and pause the lane when it flips, surfacing the pause in the return digest). |
| F5 | **`main` goes broken mid-run** | PR-7 merges; PR-8's smoke fails not because PR-8 is bad but because PR-7 introduced a regression in a different file PR-8 happens to import. | Phase 3 | **Cross-PR regression smoke** (rotating sample of K=3 prior PRs' smoke outputs, re-run by the orchestrator before PR-N opens; failure attributed to whichever prior PR caused it). |
| F6 | **Infra failure misread as code failure** | The smoke fails because the network was momentarily out; agent re-implements correct code as broken. | Phase 2 | **Failure-class JSON sidecar** (the smoke writes `out/smoke-failure.json` with `class: code | infra | unknown`); orchestrator's retry policy keys on `class` so infra failures retry without code change. |
| F7 | **Implementation drift from plan** | PR-12 plan says "add field X to schema Y"; PR-12 ships "rename module Z." | Phase 2 | **`PIVOT_DISCLOSURE: kind: scope-reduced` or `abandoned-with-replacement`** required when title/description doesn't match the diff; validator R10 enforces presence; Tier B compares plan-intent (passed in by orchestrator) against the diff. |
| F8 | **Bad PR breaks downstream PRs** | PR-3 merges with a subtle bug; PRs 4–9 build on top; PR-10 hits the bug; remediation cascades. | Phase 3 + Phase 4 | **Phase-boundary alignment artifact** (every N PRs in a lane, the orchestrator runs an aggregate smoke + diff against the plan's phase boundary; failures roll back to last-good and reopen the affected PRs); **cross-PR regression smoke** catches the bug closer to its source. |
| F9 | **Plan was wrong** | The plan calls for a feature the codebase architecturally cannot accept (e.g. a sync API on an async codebase). Agent loops trying to make it fit. | Phase 4 + Phase 5 | **Plan-disprove pre-flight** (orchestrator runs a fresh agent against the plan before the first PR, asking "name three reasons this plan would fail to merge"); plan failures are surfaced as a structured `PLAN_FAULT` artifact, the lane is paused, and the operator's return digest leads with it. |
| F10 | **Tier B model collusion** | Same model family used for implementation and Tier B; Tier B systematically misses the same kind of mistake the implementer made. | Phase 4 | **Model-diverse Tier B**: orchestrator's Tier B selector is required to pick a different `model_family:` (e.g. claude-opus implementation → claude-sonnet OR a non-Claude reviewer). The selection and family are recorded in `BHS_TIER_B_AGENT:` (already in v3.2 schema; Phase 4 adds a `TIER_B_MODEL_FAMILY:` line that the validator checks against the implementer's family). |
| F11 | **Orchestrator state corruption / partial-write / rate-limit exhaustion** | Orchestrator dies mid-write to `lane-history.jsonl` (machine reboot, OOM, network drop, GitHub API 5xx, GitHub Apps installation rate-limit exceeded). On restart it sees a truncated trailing record and either silently drops it or appends-as-if-fresh, producing a digest that under-reports work, double-counts iteration budget, or misses an in-flight pivot. Operator returns to a clean-looking digest that omits the actual state. | Phase 4 | **Atomic state-write protocol** (every `lane-history.jsonl` append is `write-temp + fsync + atomic-rename` per record, with a per-line trailing CRC32 for truncation detection); **restart recovery procedure** (orchestrator on startup scans `lane-history.jsonl` from tail, drops any truncated/CRC-failed trailing record, logs a `state_recovery` event, refuses to proceed until the operator's most recent digest has been re-emitted with the recovery delta visible); **rate-limit pause** (orchestrator wraps every `gh`/GitHub API call with a 5xx + 429 backoff and emits a `lane_pause` with `cause: rate_limit:github_5xx_repeated` (or `rate_limit:github_429_repeated`) after N=3 consecutive failures, surfacing the pause in the return digest rather than continuing on stale state); **heartbeat sentinel** (orchestrator writes a `out/orchestrator.heartbeat.json` every M=60 seconds; absence of a fresh heartbeat at digest time is a first-class digest entry, not silently absorbed). |

**§5 anti-overhead check**: this is 11 failure modes addressed by 6 new artifacts (PIVOT_DISCLOSURE, failure-class JSON, gate-output.json, phase-alignment artifact, model-family line, orchestrator state-write protocol + heartbeat) plus the orchestrator program. Every artifact maps to ≥2 failure modes (the state-write protocol covers F1 budget integrity, F4 debt-tracking integrity, and F11 corruption itself). If Tier B identifies a failure mode not in this list that is load-bearing for walk-away mode, the architecture is incomplete and should be revised.

## 3. Build order — five phases

```
Phase 1  ─►  Phase 2  ─►  Phase 3  ─►  Phase 4  ─►  Phase 5
  │            │            │            │            │
  │            │            │            └─ ships in OCR_LOCAL only
  │            │            │              (orchestrator program)
  │            │            │
  └────────────┴────────────┴── ships in public BHS kit (becomes v3.3 release)
                                                                    │
                                                                    └─ Phase 4+5 land
                                                                       in-repo as v3.4
                                                                       reference orchestrator
                                                                       and adopter docs
```

- **Phase 1** delivers the local-and-server-side merge gate (`push_gate_status.sh` + pre-push hook). Critically, **its merge under the charter substitute gate is what auto-expires the charter** (per `docs/conventions/v3.3-development-charter.md` §3). From Phase 2 onward, every PR — including subsequent v3.3+v3.4 PRs — goes through the new push-time gate that Phase 1 just installed. The charter is single-use.
- **Phases 2–3** harden the per-PR contract and the inter-PR continuity layer in the public kit.
- **Phase 4** ships the walk-away orchestrator **only** in OCR_LOCAL. The public BHS kit references it but does not bundle it (the orchestrator runs against any v3.3-conformant repo; it doesn't need to live in every repo).
- **Phase 5** is documentation, sample-audit protocol, and the v3.3 release of the public kit.

Each phase is one PR (preferred) or a small stack (≤3) where the diff would otherwise exceed reviewability. The charter requires the `Charter-Phase:` line, so Tier B can't authorize a PR that crosses phases.

## 5. Per-phase scope (the contract for the charter)

Each sub-section is the `Charter-Scope-Statement:` reference for PRs in that phase. **A PR's diff must not exceed its sub-section's deliverables list**; if it does, Tier B caps the PR at `important` per charter §2.

### 5.1 Phase 1 — local + push-time gate (kit v3.3)

**Goal**: deliver server-side-auditable enforcement of the v3.2 merge gate without paid CI minutes.

**Deliverables (exhaustive)**:

1. `scripts/push_gate_status.sh` — bash script invoked by the operator's pre-push hook OR by the orchestrator. Behaviour:
   - Reads the most recent commit's PR body (from `git log -1 --format=%B` if pushing a branch with no PR yet; from `gh pr view --json body` if a PR exists for the branch).
   - Runs `python scripts/validate_pr_brutal_honesty.py --body -` (piped) and captures exit + stderr.
   - Runs `python scripts/check_block_flag.py` and captures exit + stderr.
   - Runs `bash scripts/smoke.sh --api-only` (the existing v3.2 smoke; tier choice is the smoke's responsibility).
   - Writes a structured artifact `out/gate-output.json` (schema in §6.2) recording timestamp, three exit codes, three exit-reason summaries, and a content-hash of the PR body that was checked.
   - Pushes `out/gate-output.json` as a commit on a sibling branch `gate-evidence/<branch-name>` so it is server-side-visible (this is the "audit trail" property — the operator can `gh api` the sibling branch from any machine and see the gate result).
   - Exits 0 if all three sub-commands exited 0; exits non-zero with a one-line summary otherwise.

2. `.git/hooks/pre-push.template` — a copy-paste template the operator drops into `.git/hooks/pre-push`. Invokes `scripts/push_gate_status.sh` and refuses the push if it exits non-zero. Cross-platform notes (Windows Git Bash vs. macOS/Linux) included.

3. `INSTALL.md` updates — Step 7 "branch protection" rewritten as Step 7a (operator action: install pre-push hook from template) + Step 7b (optional: enable GitHub branch protection if the adopter does want hosted CI). Existing v3.2 Step 7 becomes Step 7b.

4. `tests/test_push_gate_status.sh` — bash test verifying the script's three-exit-code aggregation, JSON output schema conformance, and sibling-branch push (mocked git remote).

5. CLAUDE.md snippet update: a one-line addendum stating `scripts/push_gate_status.sh` is the local merge precondition for any new feature PR.

6. **`scripts/validate_v33_schema_drift.py`** — the schema-drift validator that closes the iter-5/6/7 same-gap-twice escalation root cause (see §6.0). Behaviour:
   - Loads every artifact under `docs/conventions/brutal-honesty-kit/v3.3/{enums,schemas,tables}/` and builds the canonical identifier domains: event kinds (from `enums/lane-history-kinds.txt`), cd record kinds (`enums/cd-record-kinds.txt`), lane_pause cause namespaces (`enums/lane-pause-causes.txt`), plan_fault suffixes (`enums/plan-faults.txt`), merge-authority paths (`enums/merge-authority-suffixes.txt`), state-recovery reasons (`enums/state-recovery-reasons.txt`), pivot kinds (`enums/pivot-kinds.txt`), the CD state machine + (β) predicate (`tables/cd-state-machine.yaml`), and the cycle-clock trigger (`tables/cycle-clock.yaml`).
   - Walks `docs/conventions/brutal-honesty-kit/v3.3-architecture.md` and, for every section that names an identifier from one of those domains, extracts the prose-named token set (via regex bounded to the row/list it appears in, not the whole doc) and asserts set-equality against the artifact's domain. Drift surfaces as `<doc §X.Y> names {extra} not in <artifact-path>` or `<artifact-path> declares {extra} not named in <doc §X.Y>`.
   - JSON-Schema-validates every fenced JSONL example embedded in the doc against `schemas/lane-history.schema.json` or `schemas/carried-debt.schema.json` based on the example's `kind` field; invalid examples fail the commit with the JSONSchema error pointer.
   - Verifies §6.0's authority-precedence claim mechanically: any `oneOf` branch in the schemas whose `const` discriminator value does not appear in the matching enum file fails the run (so adding a new event kind to the schema without adding it to `lane-history-kinds.txt` is structurally rejected, and vice versa).
   - Exit codes: `0` on no drift; `1` on prose-vs-artifact set mismatch; `2` on JSONL example schema-validation failure; `3` on schema-vs-enum discriminator mismatch; `4` on an artifact file being unreadable / malformed.
   - Invoked from `scripts/push_gate_status.sh` (Deliverable 1) as a fourth sub-command alongside the brutal-honesty validator, block-flag check, and smoke. Aggregation rule: any non-zero exit code from the drift validator fails the push gate.

7. **`tests/test_validate_v33_schema_drift.py`** — fixture-based regression test for Deliverable 6. Three fixture families:
   - **Known-good**: the current `v3.3/` artifacts + current `v3.3-architecture.md` produce exit 0. This is the floor: every commit that touches either side has to keep this passing.
   - **Planted prose-drift**: a temporary in-memory copy of the architecture doc with one extra plan_fault suffix word inserted into §6.5 produces exit 1 with the offending suffix and the artifact path in stderr. One sub-fixture per artifact type (enum, schema, table) to confirm each path is exercised.
   - **Planted JSONL-example drift**: a temporary architecture doc containing a fenced JSONL block with an invalid `record_id` (not UUIDv7) produces exit 2; a fenced block with an unknown `kind` produces exit 3.
   - **Malformed-artifact**: a temporary `v3.3/enums/plan-faults.txt` containing a line with uppercase letters produces exit 4 with the line number cited.
   Tests use `subprocess.run([sys.executable, "scripts/validate_v33_schema_drift.py", ...], capture_output=True)`; fixture files live under `tests/fixtures/v33_drift/` so the test is self-contained and does not mutate the real artifact directory during a run.

**Out of scope for Phase 1**:
- Anything that touches the `PIVOT_DISCLOSURE:` schema (Phase 2).
- Anything that touches block-flag computation (Phase 3).
- The orchestrator program itself (Phase 4).
- The walk-away playbook docs (Phase 5).

**Backport-compatibility constraint**: Phase 1 must not require any changes to the v3.2 validator scripts or rulebook prose. A repo running v3.2 today must be able to drop in the Phase 1 deliverables and have `push_gate_status.sh` work without breaking anything. (This is enforced by Tier B: if the diff modifies `scripts/validate_pr_brutal_honesty.py`, `scripts/check_block_flag.py`, or `rulebook/brutal-honesty-rulebook.md`, the PR exceeds Phase 1 scope.)

**Charter expiry verification step** (must be the last check Tier B performs before scoring): Tier B confirms that `scripts/push_gate_status.sh` is on the branch's tip AND that the CLAUDE.md addendum points at it AND that an installation-checklist for the pre-push hook is present in INSTALL.md AND that `scripts/validate_v33_schema_drift.py` exits 0 against the current `v3.3-architecture.md` + `v3.3/` tree AND that `tests/test_validate_v33_schema_drift.py` passes in the branch's own test run. If any of those five is missing or failing, the charter does NOT auto-expire on Phase 1 merge — Tier B caps at `important` and the PR returns to Tier A.

### 5.2 Phase 2 — per-PR contract hardening (kit v3.3)

**Goal**: make the per-PR contract carry the structured artifacts the orchestrator (Phase 4) needs to drive its state machine, and close failure modes F2/F3/F6/F7.

**Deliverables (exhaustive)**:

1. **`PIVOT_DISCLOSURE:` schema** — new optional §4 PR-body field. Schema in §6.1.
2. **Validator R10** — if the PR's title/description claims feature X but the diff does NOT implement X (heuristic: `git log -1 --format=%B` substring match against `git diff --stat` filenames), the PR body MUST contain `PIVOT_DISCLOSURE:` with `kind: scope-reduced` or `kind: abandoned-with-replacement`. Failure message: `R10: PR title implies <substring> but diff does not touch <expected file pattern>; PIVOT_DISCLOSURE: missing or wrong kind. See rulebook §4 PIVOT_DISCLOSURE schema.` Heuristic threshold and exact pattern logic specified in §6.1.
3. **Validator R11** — `PIVOT_DISCLOSURE:` field, when present, parses against the §6.1 schema (kind ∈ {deferred-on-dependency, scope-reduced, abandoned-with-replacement}, all required sub-fields present and non-empty).
4. **Validator R12** — main-precondition gate. Before validator runs the body checks, it runs `git fetch origin main && git log origin/main..HEAD --format=oneline` and refuses to validate (exit code reserved: 4) if the branch has not been rebased onto `origin/main` within the last 24 hours OR if `origin/main` has commits since the branch's merge-base that the branch does not contain. Failure message: `R12: branch is N commits behind origin/main; rebase before validating.` Rationale: prevents F5 (PR-N's smoke passing on a stale main that doesn't include PR-N-1's changes).
5. **Failure-class JSON sidecar** — `scripts/smoke.sh` is updated to emit `out/smoke-failure.json` on non-zero exit, with schema in §6.3. The smoke writes `class: code` if the failure is a Python/JS/test exception with a stack trace; `class: infra` if the failure is OOM, network timeout, missing binary, or signal-9; `class: unknown` otherwise. The orchestrator (Phase 4) keys retry policy on this field.
6. **`gate-output.json` artifact requirement** — Phase 1's `push_gate_status.sh` already writes this file; Phase 2 adds the requirement that every PR body's `EVIDENCE:` line includes the SHA of the gate-output.json artifact (so post-merge audit can prove which gate result authorized the merge).
7. **§4 template update** — `templates/pr-body.md.template` adds the `PIVOT_DISCLOSURE:` block (with placeholder text + reference to rulebook §4).
8. **Rulebook update** — §4 template section gains `PIVOT_DISCLOSURE:` field documentation; §1 lie taxonomy gains L13 (Soft-prose-claimed-as-mechanical: claiming a check, schema, validator, or artifact is mechanically enforced when the diff only adds prose, or when the authoritative artifacts already drift from the prose). Plan-deviation-without-disclosure remains an L4 specialization enforced through `PIVOT_DISCLOSURE:` rather than a second L13 definition. Per §5 anti-overhead, an existing L-row that hasn't been quoted in 6 months should be retired in the same PR — L7 (Re-summarization decay) is the candidate (it appears in §1 but is not referenced from validator rules; the operator confirms before retirement). If the operator does not confirm L7 retirement, the rulebook size grows by one row, which is acceptable for v3.3 since the §5 clause says "rarely two adaptations" and this is a structural failure mode worth keeping. Tier B checks the rulebook size delta against the §5 "9-minute read time" constraint (currently 11 minutes per v3.2 header; the new L13 + PIVOT_DISCLOSURE description must not push it past 13 minutes — if it does, prune §3 trigger phrases that haven't been quoted by name in the v3.2 cycle).
9. **`tests/test_pivot_disclosure.py`** + **`tests/test_main_precondition.py`** + **`tests/test_failure_class_sidecar.py`** — extending v3.2's existing test suite. Each test is repo-agnostic; uses synthetic PR bodies and synthetic git states.

**Out of scope for Phase 2**:
- Block-flag computation changes (Phase 3).
- Cross-PR regression smoke (Phase 3).
- The orchestrator program (Phase 4).

### 5.3 Phase 3 — inter-PR continuity (kit v3.3)

**Goal**: close failure modes F4/F5/F8 by making the inter-PR layer carry structured continuity state the orchestrator can read.

**Deliverables (exhaustive)**:

1. **Quantitative cycle clock + automatic block-flag computation** — v3.2 §6.3 defines a cycle as "1 operator-initiated session OR 5 calendar days from prior next-session.md write." Phase 3 makes this **mechanically computable** by adding `Cycle-Start:` and `Cycle-End:` ISO-8601 timestamps to the next-session.md schema and updating `scripts/check_block_flag.py` to compute the flag automatically from the cycle math instead of trusting the operator's `**Current**:` line. The operator's line becomes a sanity-check the script reports against (warning if they diverge); the script's computation is the authoritative value the orchestrator reads. Schema in §6.4.
2. **Cross-PR regression smoke driver** — `scripts/regression_smoke.py`, run by the orchestrator before opening PR-N. Selects K=3 random prior PRs from the current orchestrator lane, re-runs each PR's `SMOKE:` command (commands captured in `out/lane-history.jsonl` — see §6.5), aggregates exit codes. Failure attribution: if any of the K smokes fails, the failure is attributed to the most recent prior PR whose diff overlaps the failing smoke's covered files. The orchestrator pauses the lane and surfaces the attribution. Heuristic intentionally simple (file-overlap rather than bisect); the failure-attribution accuracy is acceptable because the artifact merely points the operator at a starting suspect, not a verdict.
3. **Phase-boundary alignment artifact** — `out/phase-alignment.md`, written by the orchestrator at every Nth PR boundary in a lane (N defined per-lane by the plan). Schema in §6.6. Records: the plan's phase summary, the actual PRs landed under that phase, deltas (PRs that landed under the wrong phase, PRs that didn't land, PRs that landed but had `PIVOT_DISCLOSURE:` of any kind), the aggregate Carried Debt at phase boundary, and a recommendation (`continue | pause-for-operator | rollback-to-last-good`).
4. **`tests/test_cycle_math.py`** + **`tests/test_regression_smoke_driver.py`** + **`tests/test_phase_alignment.py`** — extending the existing test suite. Cycle math test covers the day-6 boundary, the same-day-second-session collapsing rule, and the timestamp-not-set fallback.
5. **Rulebook update** — §6.3 prose updated to point at the script's automatic computation as authoritative; §4 template gains a `LANE_HISTORY_REF:` line (file path + entry index in `out/lane-history.jsonl`) so a single PR can be located in its lane context post-hoc.
6. **`out/lane-history.jsonl` schema** — append-only event log written by the orchestrator (one JSON line per PR open / Tier B run / merge / pivot / pause). Schema in §6.5. Lives outside `docs/` because it's machine state, not documentation; the orchestrator owns it; the public kit defines the schema so any conformant orchestrator can write/read it.

**Out of scope for Phase 3**:
- The orchestrator itself (Phase 4).
- Documentation and adopter playbook (Phase 5).

### 5.4 Phase 4 — walk-away orchestrator (in OCR_LOCAL, v3.4)

**Goal**: ship the runtime program that consumes the v3.3-conformant artifacts (PIVOT_DISCLOSURE, gate-output.json, smoke-failure.json, phase-alignment.md, lane-history.jsonl, automatic block flag) and drives the long-running multi-PR build. This is **not** part of the public BHS kit; the public kit defines the schemas, the orchestrator (in this repo) is one conformant implementation.

**Deliverables (exhaustive)**:

1. **`orchestrator/` package** at the repo root (or `tools/orchestrator/`; final path decided at PR open time). Contains:
   - `orchestrator/__init__.py`
   - `orchestrator/plan.py` — plan loader (parses a `lane-plan.yaml`; schema in §6.7)
   - `orchestrator/state_machine.py` — PR state machine (states + transitions in §10.2)

### 6.1 `PIVOT_DISCLOSURE:` (§4 PR-body field, optional but conditionally required)

Required when validator R10 fires. Multi-line YAML embedded in the PR body between explicit markers:

```
PIVOT_DISCLOSURE:
```yaml
kind: deferred-on-dependency | scope-reduced | abandoned-with-replacement
original_intent: <one sentence stating what the PR's title/description led the reader to expect>
actual_outcome:  <one sentence stating what the diff actually does>
delta_summary:   <one paragraph; what was deferred, why, and where the deferred work goes>
recovery_plan:   <one of:
                   - "follow-up PR planned: <PR-id-or-placeholder>"
                   - "carried-debt entry: CD-### (must already exist in next-session.md)"
                   - "abandoned-with-replacement: PR-### supersedes this">
operator_visible: yes | no   # is the deviation visible to the operator without reading this PR body?
```
PIVOT_DISCLOSURE_END
```

Validator R11 parses YAML between `PIVOT_DISCLOSURE:` and `PIVOT_DISCLOSURE_END`, checks all six sub-fields present and non-empty (`kind`, `original_intent`, `actual_outcome`, `delta_summary`, `recovery_plan`, `operator_visible`), checks `kind` is one of the three allowed values (`deferred-on-dependency`, `scope-reduced`, `abandoned-with-replacement`), checks `operator_visible` is `yes` or `no`, and checks `recovery_plan` matches one of the three allowed prefix patterns above (regex anchored: `^follow-up PR planned: `, `^carried-debt entry: CD-\d{3,}`, `^abandoned-with-replacement: PR-\d+ supersedes`). Failure message includes the missing/invalid field name and, for `recovery_plan`, the regex that failed.

R10 trigger heuristic: extract the first noun phrase from the PR title (regex `^[a-z(]+: (.{20,}?)(\.|$| —)` then drop common prefix words like "feat", "fix", "docs"); look for files in `git diff --name-only` containing any token from that phrase (case-insensitive substring). If zero overlap, R10 fires unless `PIVOT_DISCLOSURE:` is present with appropriate `kind`. Heuristic intentionally fuzzy: false positives are caught by Tier B who can confirm "title and diff are aligned, R10 false positive" in their justification; false negatives are caught by F7 audit at phase-boundary alignment.

### 6.3 `smoke-failure.json` (Phase 2 sidecar)

Written by `scripts/smoke.sh` only on non-zero exit:

```json
{
  "schema_version": "1.0",
  "timestamp_iso8601": "...",
  "exit_code": 1,
  "class": "code" | "infra" | "unknown",
  "class_evidence": "<one sentence; the signal that classified it>",
  "first_failing_command": "<command>",
  "stderr_tail": "<last 1KB of stderr>"
}
```

Classification rules (smoke.sh implements them; conservative — when in doubt, `unknown`):

- `code`: stderr contains a Python traceback OR a `pytest`/`vitest`/`jest` failure line OR a non-zero exit from the smoke's last-stage explicit check
- `infra`: signal-9 / signal-15 / OOM keyword in stderr / `connection refused` / `name not resolved` / a missing binary error
- `unknown`: everything else

Orchestrator retry policy (Phase 4) keys on `class`: `infra` retries up to 3× with backoff; `code` does not retry — the lane pauses; `unknown` retries 1× then pauses.

### 6.4 `next-session.md` cycle clock additions (Phase 3)

The existing schema gains two header lines above `## Block flag`:

```markdown
**Cycle-Start**: 2026-05-10T14:32:00Z
**Cycle-End-Threshold**: 2026-05-15T14:32:00Z   # Cycle-Start + 5 calendar days OR next operator-session, whichever first
```

`check_block_flag.py` reads these two header lines for the cycle clock AND reads `out/carried-debt.jsonl` (per §6.5b) for the machine-readable Carried Debt state. The block-flag computation is: if the current ISO timestamp ≥ `Cycle-End-Threshold` AND any `cd_id` in `out/carried-debt.jsonl` satisfies the post-merge-audit predicate (β) defined in `docs/conventions/brutal-honesty-kit/v3.3/tables/cd-state-machine.yaml` (the predicate is `(status == "open" AND ttl_cycles_remaining >= 1) OR (status == "blocked")`, evaluated against the forward-walked state per §6.5b derivation rules — closes iter-7 Tier B Finding 3 by treating `blocked` as an audit-attention state), the flag is automatically `BLOCKED` regardless of what the operator wrote in `**Current**:` of `docs/next-session.md`. The script's stdout includes a `WARNING: operator-set flag (CLEAR) diverges from computed flag (BLOCKED)` line on divergence, and additionally a `WARNING: docs/next-session.md Carried Debt table diverges from out/carried-debt.jsonl render` line if the human-readable table has drifted from the JSONL truth (this divergence is non-fatal — the JSONL is authoritative; the table is rerendered on next `digest_emit`). Cycle-Start is updated to the current timestamp every time `next-session.md` is committed (a pre-commit hook delivered with Phase 3 handles this; absent the hook, the operator updates it manually — divergence is itself a `WARNING`).

**Record kinds defined for Phase 4**: `cd_open`, `cd_tick`, `cd_close`, `cd_block` (mirrored verbatim in `docs/conventions/brutal-honesty-kit/v3.3/enums/cd-record-kinds.txt`). **Always-required base fields per record**: `ts` (ISO-8601 UTC), `kind` (one of the four record kinds), `cd_id` (string matching `^CD-\d{3,}$`), `crc32` (hex string of CRC32 over the JSON body excluding the `crc32` field itself — same algorithm as §6.5 lane-history.jsonl per F11; verified on read).

**Per-record-kind required-field schema**:

| kind | additional required fields | value-space / notes |
|------|---------------------------|---------------------|
| `cd_open` | `lane_history_ref` (string matching `^lane-history\.jsonl:\d+$` OR the literal `none` for Carried Debt not originating in a lane-history event), `ttl_cycles_initial` (int ≥ 1), `ttl_cycles_remaining` (int ≥ 0, initially equal to `ttl_cycles_initial`), `blocking` (bool), `status` (must be `open` on `cd_open`), `item_text` (string, the Carried Debt Item column body), `source_text` (string, the Carried Debt Source column body), `opened_at_lane_history_index` (int, the `lane-history.jsonl` line index at which this debt was opened — typically one greater than the triggering event's index) | One `cd_open` per `cd_id`; a second `cd_open` for the same `cd_id` is L4. Carried Debt opened by operator (sample-audit per §10.2, manual review, etc.) MAY use `lane_history_ref: none` or cite a non-pause event. |
| `cd_tick` | `ttl_cycles_remaining` (int ≥ 0, the decremented value), `target_cycle_id` (UUIDv7 of the `cycle_boundary` that caused the tick) | One `cd_tick` per cycle boundary while `status` remains `open`. A `cd_tick` for a `cd_id` whose terminal prior record is `cd_close` is L4. `ttl_cycles_remaining: 0` on `cd_tick` means the same cycle batch MUST emit `cd_block` unless `cd_close` lands first. |
| `cd_close` | `closed_at_lane_history_index` (int), `close_reason` (string, one of `operator_resolved`, `operator_reverted_drift`, `superseded_by_<cd_id>`, `obsolete_no_longer_applicable`, or a free-text reason — Tier B verifies the free-text reasons are not stub-rationalizations per §1 L1) | One `cd_close` per `cd_id`; a `cd_open` after `cd_close` for the same `cd_id` is L4 (reopens are a new `CD-XXX`). |

A reader that encounters a record whose `kind` is not in this table, or whose `kind`-required fields are missing, or whose `crc32` does not verify, MUST treat the record as a corruption signal (write a `state_recovery` event in `lane-history.jsonl` with `recovery_reason: crc_mismatch` or `truncated_json` or `missing_required_field` against the offending `out/carried-debt.jsonl` line, AND pause the lane), not silently ignore it.

**Current-state derivation (forward-walk, last-record-wins).** For any `cd_id`:

1. Find the most recent record for `cd_id` (walk the file forward, retain the last record seen).
2. If terminal record is `cd_open`: current state is `status: open`, `ttl_cycles_remaining` = that record's `ttl_cycles_remaining`, `blocking` = that record's `blocking`.
3. If terminal record is `cd_tick`: current state is `status: open`, `ttl_cycles_remaining` = that record's `ttl_cycles_remaining` (the decremented value), `blocking` carried forward from the most recent prior `cd_open` (a `cd_tick` MUST NOT change `blocking` — orchestrator changes to `blocking` require an operator-driven flow not defined in this schema; future extensions are L4 if added silently).
4. If terminal record is `cd_close`: current state is `status: closed`, `blocking: false` (closed debt is non-blocking by definition), `ttl_cycles_remaining: 0`.
5. If terminal record is `cd_block`: current state is `status: blocked`, `blocking: true`, `ttl_cycles_remaining: 0`. The `blocked` state is a first-class operator-attention state distinct from `open`; the post-merge audit predicate (β) recognises it explicitly (see below).

The §6.5 `digest_emit` Carried Debt predicate's clause (β) is defined authoritatively in `docs/conventions/brutal-honesty-kit/v3.3/tables/cd-state-machine.yaml` under the `audit_predicate:` block. As of iter-8 the predicate is:

> (β) := `(status == "open" AND ttl_cycles_remaining >= 1) OR (status == "blocked")`

This formulation closes iter-7 Tier B Finding 3. The prior formulation in v3.2/early-v3.3 prose required `status: open AND ttl ≥ 1`, which structurally excluded `cd_block` records (whose forward-walk yields `status: blocked, ttl: 0`) — exactly the records the audit most needs to surface. The corrected predicate adds the `blocked` disjunct explicitly so any `cd_id` requiring operator attention is matched whether its TTL has expired or not. A `cd_id` listed in `carried_debt_ids_written` whose terminal record is `cd_close` does NOT satisfy (β) — that is, the orchestrator cannot satisfy the audit predicate by closing the debt in the same `digest_emit` window; the debt MUST be in `open` or `blocked` state at the moment `digest_emit` is written. The audit predicate's evaluator is `scripts/audit_carried_debt.py` (Phase 2 deliverable per §5); its source-of-truth definition is cd-state-machine.yaml — if the YAML and this prose disagree, the YAML is authoritative (per §6.0).

**Producer responsibilities (Phase 4 orchestrator).**

The orchestrator is the sole writer of `out/carried-debt.jsonl`. Concretely:

1. **On §10.8 post-merge audit failure**: in the same orchestrator-tick as the `lane_pause` (cause `merge_authority:post_merge_invariant_violated`) and the `state_recovery` (`recovery_reason: post_merge_drift_detected`) events, append a `cd_open` record to `out/carried-debt.jsonl` with `lane_history_ref` equal to the `last_event_index` of the `lane_pause`, `ttl_cycles_initial: 1`, `blocking: true`, `status: open`. The orchestrator then proceeds to write the next `digest_emit` event with this `cd_id` in `carried_debt_ids_written` no later than `digest_emit_max_lag_seconds` (§6.7) after the `cd_open` `ts`; exceeding this window triggers the `plan_fault:digest_emit_overdue` escalation defined in the §6.5 `digest_emit` row.
2. **On cycle boundary**: a "cycle boundary" is the appending of a `cycle_boundary` event to `out/lane-history.jsonl` per the kinds table in §6.5 (definition, triggers, and ordering invariants are authoritative in `docs/conventions/brutal-honesty-kit/v3.3/tables/cycle-clock.yaml` — closes iter-7 Tier B Finding 4). Immediately after the `cycle_boundary` record is fsynced to `out/lane-history.jsonl`, and BEFORE any other event is written to either file, the orchestrator MUST append `cd_tick` records to `out/carried-debt.jsonl` as follows: for every `cd_id` whose forward-walked current state is `status: open` AND `ttl_cycles_remaining > 0`, append a `cd_tick` record with `target_cycle_id` equal to the just-written `cycle_boundary` event's `cycle_id` and `ttl_cycles_remaining` decremented by 1. For every `cd_id` whose `cd_tick` brings `ttl_cycles_remaining` to 0 AND whose `status` remains `open`, append a `cd_block` record in the same write batch (cd-state-machine.yaml transitions `open → blocked` via `cd_block`).
3. **On operator resolution** (operator-issued `cd-resolve --id CD-XXX --reason <reason>` or equivalent): append a `cd_close` record with `close_reason` set to the operator-provided value.
4. **Render `docs/next-session.md` Carried Debt table from `out/carried-debt.jsonl`**: at the end of each `digest_emit`, re-derive the human-readable Carried Debt table in `docs/next-session.md` from the current state of `out/carried-debt.jsonl` (forward-walk per the rules above). The render is a view, not a source — the orchestrator overwrites the table section on every digest; operator-introduced edits to the table prose between digest runs are preserved as "operator notes" outside the table proper but never read by any mechanical predicate. This separation is what closes the iter-5/iter-6 same-gap-twice loop: the table can drift from JSONL truth between digest runs, but the predicates ignore the table entirely.
5. **Append-only invariant**: no record in `out/carried-debt.jsonl` is ever rewritten or deleted in place; corrections to mistakes are themselves new records (typically `cd_close` with `close_reason: superseded_by_<new_cd_id>` and a fresh `cd_open` under the new `cd_id`). In-place edits are F11 corruption and MUST trigger `state_recovery`.

**Why this file exists.** The iter-5/iter-6 Tier B finding (same-gap-twice-escalate verdict from `gpt-5-codex` on `docs/conventions/brutal-honesty-kit/v3.3-architecture.md@362afe25`) was that any predicate written against `docs/next-session.md` prose (substring matching, column inspection) is soft-prose-claimed-as-mechanical (L13). The fix is structural, not prose-tightening: move the mechanical store off prose entirely. `out/carried-debt.jsonl` mirrors the `out/lane-history.jsonl` shape (append-only, CRC32-protected, forward-walk derivable) so the verifier's checks are arithmetic on parsed JSON, not regex on operator-edited markdown. `docs/next-session.md` remains the operator's primary daily-read surface but is no longer load-bearing for §6.5 / §10.8 predicates.

### 10.2 PR state machine

States: `planned`, `pre-flight-running`, `pre-flight-paused`, `tier-a-running`, `tier-b-running`, `tier-b-paused`, `merge-ready`, `merge-pushed`, `merged`, `pivoted-deferred`, `pivoted-scope-reduced`, `pivoted-abandoned`, `awaiting-dependency`, `lane-paused`.

`awaiting-dependency` is a parking state for a PR whose `pivoted-deferred` blocker (the future PR-M from F2) has been queued but not yet merged. The state distinction matters for the digest: `pivoted-deferred` is a still-open PR that needs an action; `awaiting-dependency` is a closed-but-resumable lane slot consumed by zero in-flight code work.

Transitions (full table — every state must have a defined entry path AND a defined exit path; states with no exit are L5 untested production paths):

- `planned` → `pre-flight-running`: orchestrator picks the next PR
- `pre-flight-running` → `pre-flight-paused`: pre-flight finds critical fault
- `pre-flight-running` → `tier-a-running`: pre-flight passes
- `pre-flight-paused` → `planned`: operator runs orchestrator with `--accept-faults <fault-id>,...` OR revises `lane-plan.yaml` and restarts
- `pre-flight-paused` → `pivoted-abandoned`: operator runs orchestrator with `--abandon-pr <plan-index>` indicating the planned PR is unrecoverable
- `tier-a-running` → `tier-a-running`: iteration count incremented; budget not exceeded; same-gap-twice not triggered
- `tier-a-running` → `tier-b-running`: BHS_SELF_DRAFT = 100
- `tier-a-running` → `pivoted-scope-reduced`: 5-cap exhausted; scope reduction taken
- `tier-a-running` → `pivoted-deferred`: dependency-on-future-PR detected
- `tier-a-running` → `pivoted-abandoned`: operator-issued `--abandon-pr` OR plan-disprove pre-flight re-run flags the PR as unrecoverable mid-iteration
- `tier-a-running` → `lane-paused`: same gap survived two iterations OR cumulative budget exceeded
- `tier-b-running` → `merge-ready`: BHS_OFFICIAL = 100, severity none
- `tier-b-running` → `tier-a-running`: BHS_OFFICIAL < 100; one more iteration if budget allows
- `tier-b-running` → `tier-b-paused`: F10 detection (Tier B family matches implementer); reselect Tier B
- `tier-b-paused` → `tier-b-running`: replacement Tier B agent of an allowed different family is available in the pool
- `tier-b-paused` → `lane-paused`: pool exhausted (every configured Tier B agent shares the implementer family) — see §10.7
- `merge-ready` → `merge-pushed`: §10.8 protocol step 1 (first precondition pass) succeeded AND step 2 (status-check poll) returned all-green AND step 3 (precondition recheck) succeeded; orchestrator is about to invoke synchronous `gh pr merge`
- `merge-ready` → `lane-paused`: §10.8 protocol step 1 OR step 3 found a failed precondition (cause `merge_authority:<failed_condition>` per §6.5 grammar); the merge call was NOT made
- `merge-ready` → `lane-paused`: §10.8 protocol step 2 status-check poll returned a required-check failure (cause `merge_authority:status_check_failed`) or timed out (cause `merge_authority:status_check_timeout`)
- `merge-ready` → `lane-paused`: `lane-plan.yaml` `merge_policy: operator-only` is set (cause `operator:requested_pause`, `details: merge_policy_operator_only_PR_<n>_awaiting_human_merge`); operator-resume after manual merge
- `merge-pushed` → `merged`: synchronous `gh pr merge` returned success AND step 5 confirm-merged-state (with bounded retry per §10.8) read `state: MERGED, mergedAt: <non-null>` AND `mergeCommit.oid` matches the SHA returned by `gh pr merge`
- `merge-pushed` → `lane-paused`: synchronous `gh pr merge` returned non-zero (e.g., rebase needed; not a code bug — cause `merge_authority:status_check_failed`, `details: gh_merge_returned_<exit_code>`)
- `merge-pushed` → `lane-paused`: §10.8 step 5 confirm-merged-state read `state: MERGED` but `mergeCommit.oid` disagrees with the SHA returned by `gh pr merge` (cause `merge_authority:merge_sha_mismatch`); parallel-merge race detected, post-merge invariant audit is NOT run
- `merge-pushed` → `lane-paused`: §10.8 step 5 confirm-merged-state retries exhausted without ever reading `state: MERGED` (cause `merge_authority:post_merge_state_not_MERGED`, `details: state_after_<N>_retries_<final_state>`)
- `merged` → `planned`: forward-progress invariant satisfied AND post-merge invariant audit (per §10.8 "Residual TOCTOU window") found no precondition drift; pick next PR
- `merged` → `lane-paused`: forward-progress invariant violated (cause `forward_progress:rolling_average_floor_violated`)
- `merged` → `lane-paused`: §10.8 post-merge invariant audit found one or more of the seven preconditions drifted between step-3 recheck and post-merge state (cause `merge_authority:post_merge_invariant_violated`); a `state_recovery` event with `recovery_reason: post_merge_drift_detected` in `out/lane-history.jsonl` AND a `cd_open` record in `out/carried-debt.jsonl` (per §6.5b producer responsibility 1, with `lane_history_ref` pointing at the `lane_pause`'s `last_event_index`, `ttl_cycles_initial: 1`, `blocking: true`) are emitted in the same orchestrator-tick. The matching `cd_id` MUST appear in the next `digest_emit`'s `carried_debt_ids_written` within `digest_emit_max_lag_seconds` (§6.7) or the orchestrator emits a follow-up `lane_pause` with `cause: plan_fault:digest_emit_overdue` per the §6.5 `digest_emit` row's escalation path
- `pivoted-deferred` → `awaiting-dependency`: the blocker PR-M has entered any state ∈ {`tier-a-running`, `tier-b-running`, `merge-ready`, `merge-pushed`}; orchestrator parks the deferred PR
- `pivoted-deferred` → `pivoted-abandoned`: blocker PR-M enters `pivoted-abandoned` itself; the dependent cannot recover
- `pivoted-scope-reduced` → `planned`: the reduced-scope replacement PR (next plan-index) is queued; this is a terminal exit for the scope-reduced PR (its lane-history continues to identify the original)
- `pivoted-scope-reduced` → `awaiting-dependency`: rare — when the scope reduction itself depends on another PR
- `pivoted-abandoned` → (terminal): no exit; the PR is recorded permanently as abandoned in `lane-history.jsonl` and the digest. The lane continues with the next planned PR via `planned`. (This is intentional: `pivoted-abandoned` is the explicit "we tried, gave up, moving on" sink.)
- `awaiting-dependency` → `planned`: blocker PR-M reached `merged`; orchestrator unparks the dependent and re-enters planning to retry it
- `awaiting-dependency` → `pivoted-abandoned`: blocker PR-M reached `pivoted-abandoned`
- `awaiting-dependency` → `lane-paused`: per-lane pause cap exceeded while parked (see §10.3)
- `lane-paused` → `planned`: operator-issued `lane-resume` event recorded with signoff (per §6.5 `lane_resume` schema) AND the cause that triggered the pause is no longer present (e.g. block-flag now CLEAR, rate-limit window passed, F11 `state_recovery` event written)
- `lane-paused` → (terminal): operator-issued `--end-lane` flag — orchestrator emits a final `digest_emit` event and exits cleanly

Every state transition emits a `lane-history.jsonl` event (per §6.5). Any transition not in this table is L5 by definition.

**Cycle-boundary side-effect on the PR state machine.** Cycle boundaries are not PR transitions and they do not appear in the table above; they are global clock events whose definition is the authoritative artifact `v3.3/tables/cycle-clock.yaml` (Finding 4 closure). The orchestrator emits a `cycle_boundary` event in `out/lane-history.jsonl` under exactly the three triggers enumerated in `cycle-clock.yaml` (`wrap_session_skill`, `manual_emit_cycle_boundary`, `charter_phase_pr_merged`). The `charter_phase_pr_merged` trigger fires from the `merged` → `planned` transition above when the merged PR closes a charter phase (i.e. when the PR is the last planned PR in its phase per `lane-plan.yaml`). On every `cycle_boundary` write, the orchestrator MUST — within the same orchestrator-tick and AFTER fsyncing the `cycle_boundary` line itself — append exactly one `cd_tick` record to `out/carried-debt.jsonl` for every `cd_id` whose forward-walked status is `open`. Each `cd_tick` carries `target_cycle_id: <new_cycle_boundary.cycle_id>` and `ttl_decrement: 1`; cycle-clock.yaml's "tick-batch ordering" rule rejects any `cd_tick` whose `target_cycle_id` does not match a preceding `cycle_boundary` record in `lane-history.jsonl`, and rejects any `cycle_boundary` whose `ts` is within `min_cycle_interval_seconds` of the prior `cycle_boundary`. A PR transition that should fire `charter_phase_pr_merged` but does not emit the `cycle_boundary` event (or emits the event but then fails to write the corresponding `cd_tick` batch) is L5 — the orchestrator MUST detect this on the next planning tick and emit `lane_pause` with `cause: plan_fault:digest_emit_overdue` if the unsupported gap is observed by the schema-drift validator at any digest boundary.

### 10.3 Iteration budgets

- **Per-PR cap** (existing v3.2 Tier A): 5 iterations.
- **Per-lane cumulative cap** (new): **default 100** for a lane of 30–40 planned PRs. Derivation: 30–40 PRs × ~2.5 average Tier A iterations per PR (target: most PRs hit 100 in 1–3 iterations; a few hit the 5-cap and either succeed late or pivot) = 75–100 total iterations expected; the cap is set at the upper end so the orchestrator pauses *as the budget approaches exhaustion* rather than after silent overrun. **Configurable per `lane-plan.yaml` `budget.per_lane_iterations:`** (per §6.7) — operator MUST raise the cap explicitly for plans larger than 40 PRs (rough rule: `2.5 × planned_pr_count`, rounded up to nearest 25). Reading: across all PRs in a lane, no more than the configured cap of total Tier A iterations may run. Prevents F1 cumulative.
- **Per-lane pause cap** (new): default 3. After 3 lane-paused transitions, the orchestrator escalates to operator regardless of cause and emits the digest with status `escalation_required`. Configurable per `lane-plan.yaml` `budget.per_lane_pauses:`.
- **Same-gap-survives-two-iterations** (existing v3.2 anti-spiral): orchestrator tracks Tier A iteration outputs by gap-fingerprint (sha256 of the failing rule + file:line); two consecutive identical fingerprints trigger lane-pause.

All budgets are configurable via `lane-plan.yaml` `budget:` section (per §6.7); defaults above are sized for the v3.3+v3.4 build itself (5 phases, ≤15 PRs total) and the next-realistic Claudius Maximus trial lane (~30–40 PRs).

### 10.8 Merge authority — when the orchestrator is permitted to merge a PR

The orchestrator MAY merge a PR ONLY through the synchronous, no-`--auto` protocol below. The protocol exists because GitHub's `--auto` flag separates *authorization time* (when the orchestrator checked the seven preconditions) from *merge time* (when GitHub actually performs the merge once required status checks turn green). That gap is a TOCTOU window in which the PR body, the block flag, the heartbeat, the pivot state, or another PR in the lane can change — producing a merge that violates the convention's own preconditions. The orchestrator MUST close that window.

**Merge protocol (mandatory ordering, no skipping):**

1. **Local precondition check (first pass)** — verify all seven preconditions enumerated below. On any failure: emit `lane_pause` with `cause` per the §6.5 grammar (`merge_authority:<failed_condition>`), do NOT proceed to step 2.
2. **GitHub status-check poll** — invoke `gh pr checks <pr> --required` in a loop with bounded backoff (initial 5s, max 60s, capped overall at the configured `merge_status_check_timeout_seconds`, default 1800). Three outcomes:
   - All required checks PASS → continue to step 3.
   - Any required check FAILS → emit `lane_pause` with `cause: merge_authority:status_check_failed`, do NOT merge.
   - Timeout → emit `lane_pause` with `cause: merge_authority:status_check_timeout`, do NOT merge.
3. **Local precondition recheck (second pass, mandatory)** — re-evaluate ALL seven preconditions a second time within the same orchestrator-tick. If any precondition that passed in step 1 now fails (PR body edited, heartbeat aged out, block flag flipped, pivot recorded, forward-progress invariant violated by an interleaved merge), emit `lane_pause` with `cause: merge_authority:recheck_drift_detected` and `details:` listing which precondition drifted. Do NOT merge.
4. **Synchronous merge** — invoke `gh pr merge --squash <pr>` (or `--rebase <pr>` per `lane-plan.yaml` `merge_strategy:`) WITHOUT the `--auto` flag, and await the response synchronously. The `--auto` flag is FORBIDDEN in this protocol; an orchestrator implementation that uses `--auto` is L4 (the implementation looks like it merges under the seven preconditions but actually merges later under whatever conditions hold at GitHub's auto-merge fire time).
5. **Confirm merged-state (bounded retry, SHA-reconciled)** — read `gh pr view <pr> --json state,mergedAt,mergeCommit`. The expected merge SHA from step 4's `gh pr merge` response is denoted `step4_sha`. Four outcomes, evaluated in this order (first match wins — the transient bullet MUST be checked before the SHA-mismatch bullet, otherwise a null-`mergeCommit` transient confirmation will be falsely routed to `merge_sha_mismatch`):
   - **(success)** `state: MERGED` AND `mergedAt` not null AND `mergeCommit` not null AND `mergeCommit.oid` not null AND `mergeCommit.oid == step4_sha` → success. Emit the `merge-pushed` → `merged` state transition and the `merge` event in `lane-history.jsonl` with `merge_sha: <mergeCommit.oid>`. Then proceed to the **post-merge invariant audit** described under "Residual TOCTOU window" above (any audit failure emits `cause: merge_authority:post_merge_invariant_violated`, NOT a rollback).
   - **(transient confirmation — RETRY, do not declare mismatch)** `state: MERGED` AND (`mergedAt` is null OR `mergeCommit` is null OR `mergeCommit.oid` is null) → GitHub has accepted the merge but has not yet populated the merge-commit fields in its read replica. This is an expected sub-second consistency lag, NOT a SHA mismatch. Retry under the same bounded-backoff schedule defined in the fourth bullet below. A `mergeCommit: null` payload MUST NOT be dereferenced as `mergeCommit.oid` for comparison against `step4_sha`; treating a null `mergeCommit` as `mergeCommit.oid ≠ step4_sha` and routing to `merge_sha_mismatch` is L4 (the transient state is silently relabelled as a parallel-merge race). After exhausting retries while this transient state persists, emit `lane_pause` with `cause: merge_authority:post_merge_state_not_MERGED` and `details: merged_but_fields_null_after_<N>_retries`.
   - **(SHA mismatch — only after both fields are populated)** `state: MERGED` AND `mergedAt` not null AND `mergeCommit` not null AND `mergeCommit.oid` not null AND `mergeCommit.oid ≠ step4_sha` → emit `lane_pause` with `cause: merge_authority:merge_sha_mismatch` and `details: gh_merge_returned_<step4_sha>_view_returned_<mergeCommit.oid>`. This indicates a parallel-merge race (extremely rare; signals an operator-issued manual merge or a second orchestrator instance merged between step 4 and step 5). Do NOT proceed to the invariant audit; the audit's precondition assumptions about which commit is on the branch tip are no longer valid. **Pre-condition for entering this bullet**: BOTH `mergedAt` and `mergeCommit.oid` MUST be non-null populated values. A null `mergeCommit` is routed to the transient bullet above, never to this one.
   - **(retry — non-MERGED state)** Any other state (`OPEN`, `CLOSED`, transient GitHub read returning stale data) → retry with bounded backoff. Defaults: `merge_confirm_retry_count: 3`, `merge_confirm_retry_initial_seconds: 5` (configurable in `lane-plan.yaml` per §6.7). Each retry doubles the wait up to a 30s ceiling. After exhausting retries with no `state: MERGED`, emit `lane_pause` with `cause: merge_authority:post_merge_state_not_MERGED` and `details: state_after_<N>_retries_<final_state>`. Note: a transient stale read followed by a successful retry is the expected case for this branch — it MUST NOT pause the lane on the first non-MERGED response.

**The seven preconditions** (checked in step 1 AND re-checked in step 3):

1. **Gate output** (`merge_authority:gate_output_failed` on fail): the most recent `out/gate-output.json` for the PR's branch shows `aggregate_exit_code: 0` AND `pr_body_sha256` matches the current PR body's sha256 (preventing stale gate evidence on an edited body — `merge_authority:pr_body_sha_mismatch` if the sha disagrees).
2. **Score** (`merge_authority:bhs_official_lt_100` or `merge_authority:severity_not_none`): the corresponding `lane-history.jsonl` `tier_b_run` record for this PR shows `bhs_official: 100` AND `severity: none`.
3. **Pivot status** (`merge_authority:pivot_kind_forbids_auto_merge`): either no `pivot` event has been written for this PR, OR the `pivot.kind_of_pivot` is one of `{deferred-on-dependency, scope-reduced}` AND the PR's `Charter-Scope-Statement:` (or post-charter `LANE_HISTORY_REF:` plan-intent line) explicitly acknowledges the pivot. `abandoned-with-replacement` PRs are NEVER orchestrator-merged — they are operator-only because the replacement chain is too easy to corrupt.
4. **Hook sentinel** (`merge_authority:hook_sentinel_missing`): `push_gate_status.sh --self-check` returns 0 from the orchestrator's environment, proving the pre-push hook installed per charter §3 / Phase 1 is present and bears the sentinel line. (Post-charter expiry, this is the standing precondition.)
5. **No carry-forward block** (`merge_authority:block_flag_blocked`): `python scripts/check_block_flag.py` exit 0.
6. **Forward-progress invariant** (`merge_authority:forward_progress_violated`): this merge will not violate §10.6 (i.e. the new BHS_OFFICIAL is ≥ rolling-N average).
7. **Heartbeat fresh** (`merge_authority:heartbeat_stale`): `out/orchestrator.heartbeat.json` is less than M seconds old (default M=300; configurable). A stale heartbeat means we may be a zombie process and should not act.

**This is not "GitHub auto-merge" in the sense of a generic bot:** the orchestrator is the named accountable agent for the merge, the seven preconditions are the structured gate enforced *thrice* (pre-poll, post-poll same-tick before the merge call, and post-merge audit), with the residual sub-second TOCTOU window between the step-3 recheck and the step-4 merge call explicitly acknowledged and bounded by the post-merge invariant audit (see "Residual TOCTOU window" below). Every merge writes both a `merge` event in `lane-history.jsonl` and a row in `docs/conventions/v3.3-charter-merges.md` (during the charter window). See §13 non-goals for the explicit distinction.

**Residual TOCTOU window — explicit acknowledgment.** Steps 3 (precondition recheck) and 4 (`gh pr merge`) are necessarily two separate operations. No client-side mechanism can make them truly atomic against the GitHub server, because GitHub's REST/GraphQL merge API does not expose a CAS-style "merge if these mergeability conditions still hold" primitive — `gh pr merge` itself only checks GitHub-side mergeability (status checks, branch protection, conflicts), not convention-side preconditions like the seven above. The window between step 3 completion and step 4 server-side execution is bounded by the orchestrator's network latency to GitHub (typically <1s) and is the irreducible TOCTOU surface. Concrete in-window drift scenarios:

- (a) PR body edited by operator or another agent → invalidates `pr_body_sha256` recorded in `gate-output.json`.
- (b) `out/orchestrator.heartbeat.json` ages past `M` between recheck and merge response → orchestrator was acting as a stale process at merge time.
- (c) Block flag flipped to BLOCKED by an interleaved `check_block_flag.py` invocation (e.g. another lane's debt closure).
- (d) A `pivot` event written to `lane-history.jsonl` for this PR by a parallel orchestrator instance (e.g. operator-issued `lane-pivot --pr <n>`).
- (e) Another lane's merge violating §10.6 forward-progress relative to this PR's expected rolling average.

**Mitigation — post-merge invariant audit (mandatory step-5 extension).** After step 5 confirms `state: MERGED`, the orchestrator MUST re-evaluate ALL seven preconditions one more time against the post-merge repo state. If ANY precondition that held in step 3 is now found violated, the orchestrator emits in this exact order, with the ordering, same-tick freshness window, machine-readable Carried Debt store, and Carried Debt presence mechanically enforced by four cross-referenced rules across §6.5 and §6.5b — the §6.5 `lane_pause` row's "Post-merge audit ordering" rule (steps (i)→(ii) sequencing + tick window), the §6.5 `state_recovery` row's "Post-merge audit successor rule" (conditions (a)–(d) on the successor event), the §6.5 `digest_emit` row's "Post-merge audit Carried Debt predicate" rule (the `carried_debt_ids_written` field plus clauses (α)/(β)/(γ) operating on `out/carried-debt.jsonl`), and the §6.5b producer responsibility 1 (same-tick `cd_open` write to `out/carried-debt.jsonl`): (i) a `lane_pause` event in `out/lane-history.jsonl` with `cause: merge_authority:post_merge_invariant_violated`, `last_event_index: N` (the line index this event lands at), and `details:` listing which precondition drifted; (ii) on the immediately next non-comment line of `out/lane-history.jsonl` (no intervening events of any kind), within one orchestrator-tick of (i) per `lane-plan.yaml` `orchestrator_tick_seconds:` (default ≤ 5s), a `state_recovery` event with `recovery_reason: post_merge_drift_detected` exactly; (iii) in the same orchestrator-tick as (i), a `cd_open` record appended to `out/carried-debt.jsonl` (per §6.5b producer responsibility 1) with `lane_history_ref: "lane-history.jsonl:N"`, `ttl_cycles_initial: 1`, `ttl_cycles_remaining: 1`, `blocking: true`, `status: open`, and `opened_at_lane_history_index` no greater than N+2 (allowing the slot for the `state_recovery` event); (iv) by the next `digest_emit` event written to `out/lane-history.jsonl` no later than `digest_emit_max_lag_seconds` (default 600s per §6.7) after the `cd_open`'s `ts`, the `cd_id` from (iii) MUST appear in that `digest_emit`'s `carried_debt_ids_written` list AND satisfy clauses (α)/(β)/(γ) of the §6.5 `digest_emit` Carried Debt predicate. If the window in (iv) is exceeded, the orchestrator MUST emit an additional `lane_pause` event with `cause: plan_fault:digest_emit_overdue` and `details: cd_<cd_id>_unmatched_after_<elapsed>_seconds_exceeds_max_<digest_emit_max_lag_seconds>` — this is the named, bounded escalation path that makes the verifier's refuse-to-advance state operator-visible rather than silent. Any deviation — out-of-order interleaving in `lane-history.jsonl`, gap > one orchestrator-tick between (i) and (ii), absent or wrong-kind successor, missing `cd_open` in `out/carried-debt.jsonl` for the audit-failure line index, `cd_open` with wrong `lane_history_ref` or non-`open`/non-`blocking`/zero-TTL state, absent `carried_debt_ids_written` listing, `carried_debt_ids_written` lacking any `cd_id` satisfying clauses (α)/(β)/(γ), or violation of the `digest_emit_max_lag_seconds` bound without the `plan_fault:digest_emit_overdue` escalation — is L5 per the §6.5 `lane_pause` / `state_recovery` / `digest_emit` rows AND the §6.5b record-kind schema, and the reader-side `lane-history.jsonl` verifier MUST refuse to advance past the `lane_pause` until the successor sequence is well-formed AND MUST refuse to advance past the next `digest_emit` until its Carried Debt predicate is satisfied against the machine-readable `out/carried-debt.jsonl` store (this is mechanical L5 enforcement across two JSONL files and four cross-referenced rules, not soft prose against `docs/next-session.md`).

The merge is NOT rolled back. Squash-merge to a protected branch is operationally irreversible without history rewrite, which is a higher-severity escalation than the drift itself; rolling back silently would also violate §1 evidence-rule (the `merge` event is real). Instead the drift becomes top-priority operator debt, surfaced in the next return digest's "What needs operator attention right now" section. The operator decides whether to revert in a follow-up PR or accept the drift.

**Why post-merge audit instead of true atomicity.** The brutal-honesty position: GitHub does not provide a CAS-merge endpoint, so claiming "atomic enforcement" between client-side preconditions and server-side merge would be L1 (stub-presented-as-impl). The protocol therefore (a) bounds the window as tightly as same-tick orchestration allows, (b) detects drift after the fact via the audit, (c) surfaces the drift as visible carried debt rather than silent recovery, and (d) acknowledges in this paragraph that the residual sub-second window exists. This is the v3.2 evidence-rule-consistent position.

**Operator override**: per `lane-plan.yaml` `merge_policy: operator-only`, the orchestrator skips step 4 entirely and instead emits a `lane_pause` with `cause: operator:requested_pause` and `details: merge_policy_operator_only_PR_<n>_awaiting_human_merge`. Operator merges manually; orchestrator picks up via `lane-resume` after the operator's `gh pr merge` lands.

### 10.4 Plan-disprove pre-flight

Before any PR opens in a lane, orchestrator spawns one fresh agent (model family per `tier_b_selector` rules — different family from intended implementer) and gives it:

- `lane-plan.yaml`
- a description of the codebase's current state (filesystem snapshot summary, recent commit log)
- the v3.3 rulebook + this architecture doc

Asks: *"Name three reasons this plan would fail to merge as written. For each: which PR (by index) and which failure mode (F1–F10 from the architecture doc, or 'plan-architectural' for an untyped fault). If you cannot find three, say so explicitly and state what you checked."*

Output written to `out/plan-faults.md`. If any fault is severity `critical` (the agent's own classification, validated against a small allow-list), lane is `pre-flight-paused` and the digest leads with the faults. The operator unpauses by either (a) revising the plan, or (b) accepting the faults and re-running with a `--accept-faults <fault-id>,...` flag.

### 10.6 Forward-progress invariant

After every merge:

1. Compute rolling average of `BHS_OFFICIAL` over last N=3 merged PRs (configurable).
2. Compare next-to-merge PR's `BHS_OFFICIAL` against `max(rolling_avg, min_floor)`.
3. If next PR is below: lane-pause with `cause: forward_progress:rolling_average_floor_violated`. Digest surfaces the trend.

Rationale: a clean lane has all-100s; a lane that starts dropping into 90s means something is going wrong systemically (Tier B was missing things, plan was wrong, codebase rot). Better to pause early.

### 10.7 Tier B selector

Inputs: `implementer_family` (from `BHS_SELF_DRAFT_AGENT:` parsed at PR open), `forbidden_families` (from `lane-plan.yaml`).

Selection: pick from configured Tier B agent pool any agent whose family is not in `forbidden_families` AND whose family ≠ `implementer_family`. Pool is operator-configured at lane start (e.g. `["claude-sonnet-4.6", "gpt-5", "human-self"]`).

Recorded in PR body as `TIER_B_MODEL_FAMILY: <family>` (Phase 2 schema). Validator R6 (extended in Phase 4 implementation) fails the PR if `TIER_B_MODEL_FAMILY` matches the implementer's family token.

If pool exhausts (every available Tier B agent shares the implementer family — unlikely but possible in a single-vendor environment), lane-pause with `cause: tier_b_pool:exhausted` and operator must add a different agent to the pool.

## 13. Explicit non-goals

These are out of scope for v3.3 + v3.4. Tier B should reject any PR that drifts into these:

- **Hosted CI required**: the architecture is local-and-push-time; adopters who want hosted CI keep the v3.2 ci/brutal-honesty-gate.yml; nothing forces them off it.
- **Multi-tenant orchestrator**: the orchestrator drives one operator's lanes. No SaaS, no UI, no shared state between operators.
- **Generic auto-merge bots**: the architecture forbids a generic "watch for green checks, auto-merge" bot. The orchestrator's own merge action under §10.8 is NOT a generic auto-merge bot — it is a named accountable agent whose merge is gated by seven structured preconditions (gate-output, score+severity, pivot status, hook sentinel, block flag, forward-progress invariant, fresh heartbeat), every merge writes a `merge` event to `lane-history.jsonl` and a row to `docs/conventions/v3.3-charter-merges.md`, and the operator can disable orchestrator-merge for a lane by setting `merge_policy: operator-only` in `lane-plan.yaml`. Distinction matters: a generic bot is opaque to the operator; the §10.8 merge is fully auditable post-hoc from `lane-history.jsonl` and `gate-evidence/<branch>` sibling branches.
- **A new agent type**: per §5 anti-overhead, no new MCP / skill / agent-type registration. The orchestrator is plain Python invoking existing tools (gh, git, validators, smoke).
- **Changing what counts as evidence**: §0 evidence rule is unchanged. Walk-away mode does not relax evidence; it makes evidence machine-readable.
- **Replacing the operator**: walk-away mode reduces operator interrupt frequency from "every PR" to "every digest read" (typical: end-of-day). It does not eliminate the operator's role.

## 14. Open questions for Tier B

These are honest uncertainties surfaced at architecture time. Each is either **resolved-inline** (decision recorded here, applies immediately, no further deferral) or **phase-deferred** (decision belongs to a specific later phase's PR; the architecture commits to surfacing it as a required Tier B prompt at that phase's PR open).

**Resolved inline (must be honored from Phase 1 onward):**

5. **Sibling-branch push for gate-output.json** — **RESOLVED**: Phase 1 MUST verify push capability for the `gate-evidence/*` prefix at `push_gate_status.sh` self-check time (`git push --dry-run gate-evidence/<branch>` or equivalent). If push is forbidden by branch protection, the script emits a structured `gate-evidence-push-forbidden` warning AND exits non-zero, causing the gate to fail closed (consistent with §3 of charter). Local-only gate evidence is unsafe — it cannot be cross-machine audited. The Phase 1 INSTALL.md MUST instruct adopters to either (a) allow `gate-evidence/*` push, or (b) configure an alternative evidence-storage mechanism (a tagged GitHub Gist, an S3 bucket, etc.) before installing the kit. Warn-and-continue was the wrong default; failing closed is the v3.2 evidence-rule consistent default.

"Orchestrator's own state file is corrupted" is the literal F11. Question retired.

## 15. Summary — what changes vs v3.2 in one paragraph

V3.2 enforces honesty at PR-open time with executable validators and a hard 100/100 merge gate. V3.3 (Phases 1–3) extends that enforcement (a) onto the operator's local machine via a push-time gate, (b) into structured artifacts (PIVOT_DISCLOSURE, gate-output.json, smoke-failure.json, phase-alignment.md, lane-history.jsonl) that a programmatic orchestrator can consume, and (c) into a quantitative cycle clock that removes the last operator-judgment bottleneck in Tier C. V3.4 (Phases 4–5, in OCR_LOCAL only for Phase 4) ships a reference orchestrator that uses those artifacts to drive a 30–40-PR lane unattended, plus the playbooks and Claudius Maximus trial evidence that prove the orchestrator works. The charter (`docs/conventions/v3.3-development-charter.md`) is the temporary substitute gate that lets these phases land without paid CI; it auto-expires when Phase 1 merges. Everything else in v3.2 — the lie taxonomy, the five hard rules, the three-tier Remediation Loop, the BHS scale, the operator-override mechanism — is unchanged.
