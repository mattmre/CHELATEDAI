# Report 401-500: Safety, Governance, Tool Protocols, Eval Infrastructure, And Retrieval Backends

Date: 2026-05-01

## Executive Read

The final 100 analyzed sources close the loop: if ChelatedAI is going to run self-improving agents and model-scope steering, it needs a safety and reproducibility layer as concrete as its training layer.

The strongest additions are not abstract governance docs. They are practical controls: red-team lanes, prompt-injection tests, instruction hierarchy, capability-scoped tools, artifact cards, dataset datasheets, contamination audits, MCP-style tool contracts, OTEL/OpenInference traces, and reproducible eval/data versioning.

## Key Findings

### 1. Agent safety must test tools and trajectories, not only text

HarmBench, AgentHarm, CyberSecEval, prompt-injection benchmarks, PAIR/TAP-style jailbreak generation, and Agent-Safety-style work show that tool-using systems fail through action sequences. A harmless final answer can still hide unsafe tool behavior.

ChelatedAI implication: `run_safety_testbed.py` should gain trajectory-level safety scoring, tool permission checks, and prompt-injection fixtures.

### 2. Instruction hierarchy and capability security are architectural requirements

Instruction Hierarchy, StruQ, CaMeL, OWASP, and MCP security implications all converge on one point: data, user instructions, developer policy, system policy, and tool outputs need explicit privilege boundaries.

ChelatedAI implication: add a policy stack and tool-capability manifest. Tool calls should be allowed only through declared capabilities and logged with trace evidence.

### 3. Governance can be implemented as release evidence

NIST AI RMF, NIST GenAI Profile, system cards, model cards, datasheets, safety cases, preparedness frameworks, and frontier safety frameworks can be translated into repo-native artifacts.

ChelatedAI implication: every promoted adapter, eval set, model-scope steering overlay, or agent workflow should get a compact artifact card: purpose, base, data, evals, safety checks, limitations, rollback.

### 4. Evaluation integrity needs contamination and living-red-team controls

Data contamination work, Dynabench, Inspect, HELM Safety, and dynamic jailbreak platforms show that static benchmarks decay. The repo should distinguish public benchmark scores from private regression scores and living adversarial queues.

ChelatedAI implication: add contamination audit fields and private holdout flags to eval manifests.

### 5. MCP is the right tool boundary if paired with an allowlist and traces

MCP tools/prompts/resources provide a standardized way to expose tools and prompt assets, but the protocol itself does not solve authorization or exfiltration risk.

ChelatedAI implication: use MCP-shaped contracts for tool interfaces, but enforce allowlists, JSON schema validation, capability scopes, and trace logging in the host.

### 6. Reproducibility infrastructure should stay lightweight first

MLflow, DVC, lakeFS, W&B, Phoenix, Inspect, promptfoo, DeepEval, and vector DB systems offer useful patterns. The repo should not adopt all of them. It should first implement local manifests compatible with export to heavier systems.

ChelatedAI implication: prefer repo-native JSON/Markdown manifests now, with optional adapters to Phoenix/MLflow/DVC/promptfoo later.

### 7. Retrieval backend upgrades should be benchmark-gated

Qdrant, Weaviate, Milvus, LanceDB, pgvector, MTEB, BEIR, BRIGHT, and MIRACL show viable backend and benchmark lanes. Hybrid sparse+dense retrieval is a strong addition, but backend replacement should be evidence-driven.

ChelatedAI implication: add backend capability records and benchmark slices before migrating storage.

## Expert Panel Critique

### Security Lens

MCP/tool standardization is useful only if paired with explicit capability security. Tool schemas without privilege boundaries can make unsafe capabilities easier to invoke.

### Governance Lens

Safety cases, model cards, and datasheets should be generated from actual campaign artifacts. If they are hand-written summaries, they will drift.

### Evaluation Lens

The repo needs public benchmark comparability and private regression integrity. Treat them as separate columns in reports.

### Infrastructure Lens

Optional integrations should remain optional. The core system should run from local manifests, local traces, and local artifacts.

## Final Realignment

After 500 analyzed sources, the best strategic shape is:

1. evidence-first adaptive control,
2. reversible overlays before base edits,
3. local runtime abstraction before runtime commitment,
4. trace-graded campaigns before autonomous promotion,
5. tool-capability scopes before agent autonomy,
6. artifact cards and datasheets before release claims,
7. targeted hard negatives before broad synthetic self-training.

This is the practical path to aggressive improvement without turning the repo into an unbounded self-modifying system.
