# Report 301-400: Self-Evolving Systems, Synthetic Data, Local Runtime, And Overlay Efficiency

Date: 2026-05-01

## Executive Read

The fourth 100 analyzed sources add two constraints to the roadmap.

First, self-evolving systems are viable only if their generated data, generated prompts, generated workflows, and generated code are treated as untrusted candidates. Recursive synthetic data collapse, self-reward collapse, and prompt/workflow overfit are recurrent failure modes.

Second, Model-Scope will need a practical runtime lane. The literature and systems work point to a simple default: use an OpenAI-compatible local server abstraction, benchmark vLLM first, keep llama.cpp/Ollama as fallbacks, and use LoRA/QLoRA/PEFT overlays as the default trainable artifact class.

## Key Findings

### 1. Self-update loops need anti-collapse controls

Self-rewarding models, self-play fine-tuning, self-instruct pipelines, synthetic data controllers, and recursive data-collapse papers all show that self-generated data is useful but dangerous. The generated set must have provenance, diversity quotas, external holdouts, and anti-recursion checks.

ChelatedAI implication: generated examples should record source lineage and synthetic-generation depth. Promotion should block if a candidate is trained mostly on its own descendants.

### 2. Prompt and workflow optimization should be executable, versioned, and evaluated

OPRO, PromptBreeder, EvoPrompt, APE, PromptWizard, AutoPDL, AFlow, and prompt-program work show that prompt optimization is a real search space. But the unit of improvement must be a runnable prompt/program variant with metrics, not a prose suggestion.

ChelatedAI implication: add prompt/program candidate artifacts with inputs, outputs, scorecards, parentage, and rollback.

### 3. Hard-negative generation is a direct near-term fit

SyNeg, GPL, ANCE, RocketQA, SimANS, InPars-style work, and synthetic query generation all map cleanly to Engine-Scope negatives. The repo already has negative-generation surfaces; the next step is graded negative provenance and evaluator filtering.

ChelatedAI implication: upgrade `engine_scope_negatives.py` to track negative source type, ambiguity grade, generator, verifier, and false-negative risk.

### 4. Local serving should be abstracted behind one stable client

vLLM, SGLang, TensorRT-LLM, llama.cpp, Ollama, and OpenAI-compatible local servers all show different strengths. The repo should not bind Model-Scope to one runtime too early.

ChelatedAI implication: use an OpenAI-compatible local-server client as the serving boundary, with runtime capability records for hooks, KV behavior, batching, and adapter support.

### 5. LoRA/QLoRA/PEFT should be the default persistent training artifact

LoRA, QLoRA, PEFT, DoRA, PiSSA, aLoRA, Arrow routing, S-LoRA, Punica, and LoRAX reinforce the overlay-first policy. Adapters are the right unit for reversible training, A/B evaluation, and rollback.

ChelatedAI implication: make adapter artifacts first-class: manifest, base model hash, training data lineage, eval traces, merge policy, rollback metadata, and activation conditions.

### 6. Runtime efficiency matters because evaluation loops are expensive

PagedAttention, prefix caching, speculative decoding, prompt lookup decoding, KV quantization, StreamingLLM, KIVI, H2O, SnapKV, and MInference all matter because ChelatedAI's roadmap depends on repeated replay and evaluator passes.

ChelatedAI implication: add runtime-benchmark profiles for replay-heavy, RAG-heavy, long-context, and adapter-heavy workloads.

## Expert Panel Critique

### Self-Improvement Lens

The system should never directly trust its own generated lessons, prompts, or data. The correct posture is evolutionary search under external scoring and replay, not autonomous acceptance.

### Data Quality Lens

Synthetic data is most valuable where the repo already has failure signatures. Generic synthetic examples are less useful than targeted hard negatives tied to active blocker features.

### Runtime Lens

OpenAI-compatible local serving is the right seam for operational simplicity, but true Model-Scope hooks still require deeper runtime integration. Keep serving abstraction and hook runtime capability records separate.

### Training Lens

LoRA/QLoRA are the right default. More exotic adapter methods should earn their way in through the same benchmark matrix, not through architectural enthusiasm.

## Explosive Realignment Potential

After 400 sources, the strongest implementation lane is:

1. make all trainable improvements adapters or prompt/program artifacts,
2. serve them through a runtime capability abstraction,
3. generate targeted hard negatives from real failure signatures,
4. train/evaluate candidates under replay,
5. reject anything with synthetic recursion, reward divergence, or safety regression.

This keeps the system aggressive in search but conservative in persistence.
