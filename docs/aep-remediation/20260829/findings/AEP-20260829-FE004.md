## Defect evidence

Five primary tabs are click-only `div` elements with no role, tabindex, selected state, panel linkage, or key handling. `switchTab` relies on ambient `event.target`. Static parsing confirms the controls are non-focusable, blocking keyboard access to four of five main views.

Copy-paste inspection:

```powershell
rg -n 'class="tab"|function switchTab|aria-selected|role="tab"|tabindex' dashboard/index.html
```

Expected current evidence: five `div.tab` controls and ambient `event.target`, with no tab role, tabindex, or selected-state wiring.

Root cause: visual containers were used as controls without native semantics. Status is blocked until the dashboard slice owns the real keyboard/browser and accessibility harness required by AC1–AC3.

1. Use native buttons in a `tablist`, connect `aria-controls`/`aria-labelledby`, and manage `aria-selected`.
2. Implement arrow/Home/End and activation behavior without ambient global event.
3. Add keyboard-only browser coverage and a screen-reader smoke.

**AC1:** every tab is focusable and operable without pointer. **AC2:** selected/tab-panel semantics remain synchronized. **AC3:** mouse behavior and deep content remain intact. Verification: real browser keyboard traversal plus automated accessibility checks. Dependencies: include in the dashboard browser-smoke slice.
