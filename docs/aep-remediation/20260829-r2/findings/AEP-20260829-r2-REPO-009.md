## Defect evidence and commands

`refreshData()` starts summary and events requests together. Each successful request calls the same global `clearError()`, while either failure calls `showError()` on one shared banner. Completion order therefore controls truth: a later successful sibling can remove a real partial failure while the failed panel remains stale or loading.

```powershell
rg -n -A 18 -B 4 'async function loadSummary|async function loadEvents|function showError|function clearError|async function refreshData' dashboard_server.py
rg -n 'loadSummary|loadEvents|refreshData|showError|clearError' test_dashboard_server.py dashboard/index.html
if ($LASTEXITCODE -eq 1) { 'NO_CLIENT_TESTS' }
python -m unittest test_dashboard_server -v
```

Expected current evidence: both independent success paths call the singleton clear function, both failure paths write the singleton banner, and the refresh starts them as siblings. No client test covers opposite completion orders or partial failure state.

## Root cause and atomic fix steps

Error state is global and imperative even though request state is per resource and concurrent.

1. Model summary and events request state independently with keyed loading/success/empty/error values.
2. Derive any aggregate banner from the set of active resource errors; one resource success may clear only its own error.
3. Preserve last-known data with an explicit stale marker, or clear it according to a documented policy; never leave ambiguity between current and old data.
4. Add deterministic deferred-promise tests for both completion orders, dual failure, retry, and valid empty responses.

## Acceptance criteria

- **AC1:** an events failure remains visible after a later summary success, and the symmetric ordering behaves identically.
- **AC2:** retry success clears only the recovered resource's error and cannot erase another active failure.
- **AC3:** each panel mechanically distinguishes loading, valid empty, current success, stale-with-error, and unavailable.
