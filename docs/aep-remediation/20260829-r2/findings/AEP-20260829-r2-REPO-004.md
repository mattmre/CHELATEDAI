## Defect evidence and commands

The callback timeout returns control while its daemon thread remains alive. That thread still holds the mutable `Finding` and can change it after the orchestrator has reported the item blocked. The same execution model cannot revoke filesystem, service, or remote side effects either.

Expected current evidence: the first line reports the finding blocked with an empty commit; after release, the worker finishes and `commit_hash` becomes `MUTATED_AFTER_TIMEOUT` while status remains blocked. Unit tests do not revoke the worker's authority.

## Root cause and atomic fix steps

A thread join timeout is treated as cancellation even though Python cannot forcibly cancel a running thread and shared mutable objects remain reachable.

1. Move callback execution into an isolation boundary with explicit cancellation/termination semantics, or redesign callbacks as cooperative tasks with an enforced cancellation token and no direct tracker mutation.
2. Give workers immutable inputs and accept outputs only through a generation-scoped commit protocol after successful completion.
3. On timeout, revoke result acceptance, terminate/reap the owned worker where supported, and record any external-effects state as unknown until reconciled.
4. Add late-return, late-mutation, exception, process-termination, and external-effect reconciliation tests on Windows and Linux.

## Acceptance criteria

- **AC1:** a timed-out callback cannot mutate tracker state or have a late result accepted.
- **AC2:** the orchestrator can prove the owned execution unit is terminal, or reports an explicit unknown-effects state that blocks subsequent phases.
- **AC3:** concurrent callbacks cannot cross-write findings or verification receipts across generation boundaries.
