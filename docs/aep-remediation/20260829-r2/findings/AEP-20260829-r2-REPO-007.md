## Defect evidence and commands

The method sets `_adaptive_threshold_enabled = True` before validating inputs. A validation exception therefore leaves adaptive mode enabled with prior/partial settings. Bounds receive no type, finiteness, positivity, or ordering validation, so `min_bound > max_bound` is accepted and later clamp behavior no longer represents the documented safety interval.

Expected current evidence: a comparison `TypeError`, then `enabled_after_failed_enable True`; a second call reports `reversed_bounds_enabled True 1.0 0.1`. The 23 focused tests pass because they cover clamping of three fields but not atomic failure or bound relationships.

## Root cause and atomic fix steps

Validation and mutation are interleaved, and the configuration validators cover individual scalar ranges without validating the bounds as a pair.

1. Validate and normalize all proposed values into local immutable state before acquiring the mutation lock.
2. Require numeric finite bounds with `0 <= min_bound <= max_bound`; define whether zero is permitted and enforce the same rule in configuration loading.
3. Commit all fields and the enabled flag in one locked state transition; emit the enabled event only after commit.
4. Add invalid-type, nonfinite, reversed/equal bound, partial-update rollback, and concurrent read/enable tests.

## Acceptance criteria

- **AC1:** any invalid input leaves enabled state and every adaptive parameter byte-for-byte unchanged.
- **AC2:** reversed or nonfinite bounds are rejected before mutation and before logging an enabled event.
- **AC3:** a valid configuration commits atomically and threshold updates always clamp within the declared ordered interval.
